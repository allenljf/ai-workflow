# 在既有專案導入

**不要一次全開。** 既有專案一定有大量違規，全開會讓每個 PR 都紅，兩週內就會有人把檢查關掉。

---

## 第 0 步：先看全貌，不做任何事

```bash
python3 android-dev-guide/tools/check-rules.py --all
```

把數字記下來。這是基準線，不是待辦清單。

看到幾百處違規是正常的 —— 這些規則涵蓋 Android 過去五年的演進，任何有年紀的專案都會踩到。
**這個數字不代表程式碼很爛，代表它活得夠久。**

---

## 第 1 步：只對新程式碼生效（第 1 週）

只啟用 `enforce: new-only` 的規則，既有檔案完全不動。

```bash
# 只檢查這次改動的檔案
python3 android-dev-guide/tools/check-rules.py --staged
```

先不要擋 commit，讓大家看到輸出就好：

```bash
# .githooks/pre-commit
python3 android-dev-guide/tools/check-rules.py --staged || true
```

**這一週的目標是讓團隊習慣看到這些訊息，不是修東西。**

---

## 第 2 步：擋新違規（第 2–3 週）

確認誤報都處理完後，把 `|| true` 拿掉，讓 MUST 級違規擋 commit。

同時接進 CI：

```yaml
- run: python3 android-dev-guide/tools/check-rules.py --diff origin/main --format github
```

此時的規則是「新增的檔案要乾淨」，既有檔案仍然不管。

**判斷是否可以進下一步**：連續兩週沒有人因為誤報而卡住。

---

## 第 3 步：觸碰即修（第 4 週起）

啟用 `enforce: new-only+on-touch`：你改到的那個函式／區塊要一併修正。

邊界要講清楚，否則會失控：

| 範圍 | 要不要修 |
|---|---|
| 你新增的程式碼 | 修 |
| 你改到的那個函式 | 修 |
| 同一個檔案其他沒動到的地方 | **不修** |
| 同一個模組其他檔案 | **不修** |

如果修一條違規會牽動十個檔案，那它不屬於 on-touch，記到待辦清單另案處理。

---

## 第 4 步：批次清理（持續）

從 `--all` 的結果挑出「機械式、低風險、高數量」的項目，每項開一個獨立 PR。

好的第一批候選（改動模式固定、行為不變）：

| 項目 | 為什麼適合先做 |
|---|---|
| `collectAsState` → `collectAsStateWithLifecycle` | 純替換，行為只會變好 |
| public Mutable 狀態加 `_` 前綴 + `asStateFlow()` | 改動局部，編譯器會抓出所有呼叫點 |
| `LazyColumn` 的 `items` 補 `key` | 單行改動 |
| 空 `catch {}` 補上處理 | 逐一檢視，但每處都獨立 |
| 設計系統元件補 `modifier` 參數 | 修一次全庫受益 |

**不適合批次做的**（行為可能改變，需要逐案驗證）：

- `notifyDataSetChanged` → DiffUtil（動畫、捲動位置、選取狀態都可能變）
- 大範圍的 DI 框架遷移
- 資料層錯誤模型統一
- RxJava → Coroutine

這些需要獨立規劃，不要放進「批次清理」的心智框架裡。

---

## 什麼時候該把規則調鬆

有些規則在你的專案就是不適用。這很正常，直接標 `exempt` 並寫理由：

```yaml
- id: some-rule
  enforce: exempt
  reason: "本專案的 base class 帶必填建構子參數，此規則物理上無法達成（見 ADR-012）"
```

**標 exempt 比放著不管好** —— 它留下負面訊號，讓後來的人（和 AI）知道「這是評估過的決定」，
而不是「沒人注意到」。被整組刪掉的規則會讓人重新引入同樣的問題。

同樣地，如果某條規則的前置條件在你的專案不存在（例如沒有統一的 dispatcher provider），
**不要讓它懸空**。要嘛先做那個小基建，要嘛把規則改寫成「在缺少該基建時的替代做法」。
懸空的規則等於沒有規則，卻讓人以為有。

---

## 常見的導入失敗模式

| 模式 | 後果 | 怎麼避免 |
|---|---|---|
| 第一週就全開 | 所有 PR 都紅，兩週內被關掉 | 照上面的四步 |
| 規則沒有 enforce 分級 | 開發者面對既有檔案只能猜，要嘛不敢動要嘛過度重構 | 每條都標 enforce |
| 誤報沒人處理 | 大家學會無視輸出 | 誤報優先於新規則，一發現就修 pattern 或標豁免 |
| 只有文件沒有自動檢查 | 三個月後沒人記得 | 至少把 MUST 級接進 CI |
| 只有自動檢查沒有文件 | 只知道被擋，不知道為什麼、該怎麼改 | 每條違規訊息都要指向對應的 guides/ |
| 規則與程式碼範例對不上 | 照抄會編譯失敗，信任度歸零 | 範例一律從專案實際程式碼驗證過再寫 |

最後一項最容易發生也最傷 —— 一旦有人照著規則的範例寫卻編譯失敗，整份指南的可信度就沒了。
