# Checklist · 修改既有程式碼（重構／修 bug）

這份的重點不是「改好功能」，而是**劃清該改到哪裡**。既有專案一定有大量違規，
不劃界線的話一個小修改會變成兩百行的重構。

## 先劃界線

- [ ] 列出本次**真正需要修改**的檔案（修 bug 的話：造成問題的那幾個）
- [ ] 這份清單就是 `on-touch` 的邊界 —— 清單外的檔案不動

| 範圍 | 動不動 |
|---|---|
| 你新增的程式碼 | 100% 符合準則 |
| 你改到的那個函式／區塊 | 符合 `new-only+on-touch` 級規則 |
| 同一個檔案其他沒動到的地方 | **不動** |
| 同一個模組其他檔案 | **不動** |

- [ ] 若修一條違規會牽動十個檔案 → 它不屬於 on-touch，記到待辦另案處理

## 修 Bug 專用

- [ ] **先寫出能重現 bug 的測試**（紅燈），再修
- [ ] 修完該測試轉綠，且**沒有註解掉或放寬任何既有斷言**
- [ ] 確認的是根因，不是讓症狀消失
- [ ] 同類問題在別處還有沒有？有的話寫進 PR 描述（不一定要一起修）
- [ ] 沒有為了讓測試過而改測試而非改程式碼

## 重構專用

- [ ] 重構前後**行為不變**（有測試保護；沒有的話先補測試再重構）
- [ ] 重構與功能變更**分開 commit**
- [ ] 沒有順手改無關的檔案
- [ ] 若改變公開 API，呼叫端影響範圍已確認

## 順手修的品質底線

在你改到的區塊內，這些低風險高收益，**應該順手修**：

- [ ] `collectAsState()` → `collectAsStateWithLifecycle()`
- [ ] public Mutable 狀態 → private `_x` + 唯讀對外
- [ ] 空 `catch {}` → 至少記錄或轉 domain error
- [ ] `catch (e: Exception)` 補上 `CancellationException` 處理
- [ ] hardcode 的尺寸／顏色 → 設計系統 token
- [ ] `items` 補 `key`
- [ ] 測試裡的 `Thread.sleep` → `advanceUntilIdle()`
- [ ] 硬編碼的使用者可見文案 → 字串資源

這些**不要**順手修（風險大於收益，或會擴散）：

- [ ] 改共用的 base class（會影響所有子類）
- [ ] 改共用 model 的型別
- [ ] 改 DI 既有綁定
- [ ] `notifyDataSetChanged` → DiffUtil（動畫、捲動位置、選取狀態都可能變）
- [ ] 大範圍的框架遷移（RxJava → Flow、DI 框架替換）
- [ ] 升套件版本

## 碰到大量既有違規時

- [ ] 用 `check-rules.py` 確認該規則的 `enforce` 級別
- [ ] `migrate` 級的**不要**在這個 PR 修，記到待辦清單
- [ ] 待辦要寫清楚：規則 id、檔案、為什麼不在本次修
- [ ] PR 描述說明「本次刻意不修什麼、為什麼」

## 收尾

- [ ] 編譯 + 相關測試通過
- [ ] `python3 android-dev-guide/tools/check-rules.py` 無必修項
- [ ] 沒有讓既有測試變紅或被 `@Ignore`
- [ ] PR 的 diff 沒有超出第一步列出的檔案清單（超出的要說明）
